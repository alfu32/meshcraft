# T59 — GPUI + raylib-rs viewport integration proof

Status: **In progress** (started 2026-10-19). This is the first task for the accepted desktop stack; see [ADR-06](../../decisions/ADR-06-gpui-raylib.md), [the viewport/UI contract](../../UI-3D_renderer.md), and [issue #21](https://github.com/alfu32/meshcraft/issues/21). Do not begin the full shell migration before the viewport proof passes.

## Required proof

- Start a minimal GPUI host and render a live raylib-rs frame in the actual central content rectangle, without continuous GPU-to-CPU framebuffer readback.
- Verify clip/bounds, resize and DPI alignment, keyboard focus, pointer capture/routing, the active Linux Wayland or X11/XWayland backend, and clean close/resource destruction.
- Keep camera movement and pointer previews local at frame rate. Define typed, renderer-neutral viewport input/events and revisioned snapshot/delta synchronization.
- Record exact Rust, GPUI, component and raylib revisions, platform/display backend, reproduction commands, measurements and limitations. Do not claim Windows/macOS support without separate checks.

## Implementation boundary

The command registry, command IDs, JSON schemas, document and transactions remain independent of GPUI and raylib. The current desktop session controller must move behind the headless session contract; OS dialogs become host-effect requests. The production path cannot fall back to a CPU frame-copy viewport.

## Linux proof results (2026-10-19)

The isolated prototype is in `experiments/stack-gpui-raylib/`. It pins GPUI 0.2.2, raylib 6.0.0, raw-window-handle 0.6.2 and x11rb 0.13.2; Rust is 1.99.1 and Cargo is 1.99.1. It was run on Ubuntu 25.10, kernel 6.17.0-41-generic, Intel HD Graphics 530 / Mesa 25.2.8, in a Wayland desktop session forced onto X11/XWayland for both windows. The launch command is `env -u WAYLAND_DISPLAY cargo run --manifest-path experiments/stack-gpui-raylib/Cargo.toml`. Linux builds also need `libxkbcommon-x11-dev`; the proof locally patches xattr 0.2.3's Linux `ENOATTR` reference to `ENODATA`.

- **Native hosting: passed on this host.** `xwininfo` confirmed the raylib X11 window is a child of the GPUI client and occupies its central viewport rectangle. At 1400×900, the child was 970×836 at (170, 38). X11 clips the child to its parent; a dedicated clipping/occlusion stress case remains untested.
- **Resize: passed on this host.** After resizing GPUI to 1200×760, its bounds observer updated the raylib child to 770×696 at (170, 38). A unit test also checks 2× scale conversion; physical HiDPI hardware was not available.
- **Input: basic interaction passed.** Left-drag orbit, wheel zoom and `R` reset are handled in raylib and represented by typed, renderer-neutral input events with protocol version and monotonic sequence. Camera changes stay in the viewport loop. The child window receives pointer and keyboard input directly; GPUI-to-viewport focus arbitration is not implemented.
- **Close: passed after adding a shutdown barrier.** GPUI stops and joins the raylib loop before closing its X11 parent. The child is unmapped/reparented for GL cleanup. A live close left no process running and emitted no X11 `BadWindow` error.
- **No CPU image copy: passed by implementation inspection.** The viewport is a native OpenGL child window; no framebuffer readback or GPUI image upload occurs.

## Remaining gate items

Keep T59 **in progress**. This proves feasibility only for the local X11/XWayland path. GPUI 0.2.2's X11 raw-window-handle implementation is unimplemented, so this spike discovers the GPUI window by process/title and reparents the raylib window; that implementation-specific workaround needs a supported production integration decision. No native Wayland, Windows, macOS, physical high-DPI, or GPUI Component ecosystem test has been done. The documented `ViewportSceneSnapshotV1` / `ViewportSceneDeltaV1` contract is not implemented in the prototype; only the input envelope is. The shell is a visual mock, not the production JSON-driven command/settings UI, and no latency or frame-time benchmark has been taken.

Checks run: `cargo test --manifest-path experiments/stack-gpui-raylib/Cargo.toml` (3 passed), `cargo check --manifest-path experiments/stack-gpui-raylib/Cargo.toml`, live launch/resize/close as above, and `python3 docs/rewrite/scripts/verify_plan.py`. Complete the scene synchronization and supported integration decision, then rerun the platform/focus checks before marking T59 done or starting T60. T60 removes retired Bevy/egui code only after replacement behavior passes C39–C41.
