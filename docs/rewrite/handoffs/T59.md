# T59 — GPUI + raylib-rs viewport integration proof

Status: **In progress** (started 2026-10-19). This is the first task for the accepted desktop stack; see [ADR-06](../../decisions/ADR-06-gpui-raylib.md), [the viewport/UI contract](../../UI-3D_renderer.md), and [issue #21](https://github.com/alfu32/meshcraft/issues/21). Do not begin the full shell migration before the viewport proof passes.

## Required proof

- Start a minimal GPUI host and qualify the best live raylib-rs presentation path in the actual central content rectangle. The current candidate uses an offscreen target copied into a normal GPUI image component; it must meet the 25 FPS floor (40 ms/frame) and target 30–60 FPS.
- Verify clip/bounds, resize and DPI alignment, keyboard focus, pointer capture/routing, the active Linux Wayland or X11/XWayland backend, and clean close/resource destruction.
- Keep camera movement and pointer previews local at frame rate. Define typed, renderer-neutral viewport input/events and revisioned snapshot/delta synchronization.
- Record exact Rust, GPUI, component and raylib revisions, platform/display backend, reproduction commands, measurements and limitations. Do not claim Windows/macOS support without separate checks.

## Implementation boundary

The command registry, command IDs, JSON schemas, document and transactions remain independent of GPUI and raylib. The current desktop session controller must move behind the headless session contract; OS dialogs become host-effect requests. The offscreen renderer publishes only its latest frame so GPUI never builds a queue of stale images. Keep viewport input and camera interaction local to the high-frequency renderer loop; send model edits and scene deltas through typed headless session contracts.

## Linux proof results (2026-10-19)

The isolated prototype is in `experiments/stack-gpui-raylib/`. It pins GPUI 0.2.2, GPUI Component 0.5.1, raylib 6.0.0, raw-window-handle 0.6.2 and x11rb 0.13.2; Rust is 1.99.1 and Cargo is 1.99.1. It was run on Ubuntu 25.10, kernel 6.17.0-41-generic, Intel HD Graphics 530 / Mesa 25.2.8, in a Wayland desktop session forced onto X11/XWayland for both windows. The launch command is `env -u WAYLAND_DISPLAY cargo run --manifest-path experiments/stack-gpui-raylib/Cargo.toml`. Linux builds also need `libxkbcommon-x11-dev`; the proof locally patches xattr 0.2.3's Linux `ENOATTR` reference to `ENODATA`.

- **Native hosting: passed on this host.** `xwininfo` confirmed the raylib X11 window is a child of the GPUI client and occupies its central viewport rectangle. At 1400×900, the child was 970×836 at (170, 38). X11 clips the child to its parent; a dedicated clipping/occlusion stress case remains untested.
- **Resize: passed on this host.** After resizing GPUI to 1200×760, its bounds observer updated the raylib child to 770×696 at (170, 38). A unit test also checks 2× scale conversion; physical HiDPI hardware was not available.
- **Input: basic interaction passed.** Left-drag orbit, wheel zoom and `R` reset are handled in raylib and represented by typed, renderer-neutral input events with protocol version and monotonic sequence. Camera changes stay in the viewport loop. The child window receives pointer and keyboard input directly; GPUI-to-viewport focus arbitration is not implemented.
- **Close: passed after adding a shutdown barrier.** GPUI stops and joins the raylib loop before closing its X11 parent. The child is unmapped/reparented for GL cleanup. A live close left no process running and emitted no X11 `BadWindow` error.
- **Native-child readback: avoided.** This path uses a separate OpenGL child window, but its native stacking put GPUI menus/popovers underneath it. The offscreen-image trial below solves that composition problem, at the cost of CPU readback and GPUI upload.

## Offscreen image presentation trial (#21, 2026-10-19)

The isolated `src/bin/offscreen_image.rs` proof renders a cube and grid into raylib 6 `RenderTexture2D`, reads its RGBA pixels, converts/flips them into GPUI's BGRA `RenderImage`, and displays the image through a normal GPUI `img()` element. A GPUI overlay badge stays above the image, confirming that this path fixes the menu/viewport stacking defect from the native child-window proof. The frame bridge retains only the latest image.

The optimized Linux proof ran at 1280×800 on X11/XWayland in the current Ubuntu 25.10 session, using Intel HD Graphics 530 with Mesa 25.2.8. `env -u WAYLAND_DISPLAY cargo run --release --manifest-path experiments/stack-gpui-raylib/Cargo.toml --bin offscreen_image` sustained 59–60 new images/sec in the GPUI consumer counter. Raylib render, readback, pixel conversion and publication were typically 4–12 ms per frame, with occasional samples near 18 ms. This meets the user's 25 FPS minimum and 30–60 FPS target for the simple proof scene. The earlier debug run's ~90 ms number did not represent optimized release behavior.

This is not yet production acceptance. The proof uses a synthetic cube rather than the document scene, keeps the render target at a fixed size, and does not route viewport input or test pointer feedback, DPI, resize, sustained memory behavior or the dense-array C41 scene. Implement and measure those before cutting over the renderer. The previous native child-surface implementation remains documented as an alternative, but its z-order does not satisfy the menu requirement.

## Shell navigation and orbit update (#21, 2026-10-19)

The prototype shell lays out the full CAD-style surface for review: text menus, ribbon tabs and command groups, the categorized tool palettes, and the stacked selection/object/model/UI/architecture/HVAC/hotspot/random/tutorial/shader/help settings panels. The text menus open populated dropdowns, and the ribbon tabs switch between their own populated groups. Menu entries and command buttons remain disabled, with stable hierarchical IDs such as `toolbar/modification/move` or `ribbon/arrays/spread/linear-array`; setting values are inert display controls. This is an interactive navigation/layout prototype, not the production JSON-driven UI.

The camera applies horizontal mouse motion as target-centered yaw and vertical motion as target-centered pitch, clamped to ±85°; a positive downward mouse delta increases pitch. Orbit preserves the target and distance. Issue [#22](https://github.com/alfu32/meshcraft/issues/22) records the corrected vertical drag direction. Unit tests cover both directions, the fixed target, and preserved radius. The shell header is now 140 px high with 230 px and 330 px sidebars, so unit tests expect the 1400×900 canvas at (230, 140) with size 840×734. The previous live resize/child-bounds check used the smaller shell; rerun live after this layout expansion to validate the new native child bounds.

## 0.33.8 — Persistent GPU meshes, shader lines and shared instances

The [Solidcraft source review and authorized scope](gpu-renderer-analysis.md)
are retained separately from Meshcraft's runtime evidence. The native renderer
now keeps indexed local-space face meshes and endpoint ribbons in application-owned
OpenGL buffers. Raylib's 16-bit index range is handled by triangle-aligned chunks;
line batches also chunk without splitting a ribbon. GPU resources are owned and
released on the existing raylib worker/context thread.

Scene groups share identical effective display geometry, checking full payload
content after hashing. A local origin separates translated copies from their
mesh data, so repeated architectural pieces can share as well as object
prototypes. World transforms, mirrored orientation, selection and external-edit
tint are separate per-instance buffers. Hotspot/script geometry variants get
different groups. Unchanged buffers survive document snapshot replacement and
instance moves; removed/unreferenced groups release their resources. Camera,
line color preference and line width changes do not upload geometry. Shadow
rendering reads the same opaque meshes with the light camera.

Main model lines, selected boundaries/bounds and generic tool preview ribbons
are expanded in a vertex shader, with clipping before perspective division.
Full-object mesh wireframes are also built once in local space and instanced;
only explicitly selected face boundaries need an additional world-space overlay.
Reference/preview buffers persist while their geometry stays unchanged. Small
cursor/guide/direction-marker helpers retain their existing drawing paths.
Selection does not duplicate or tint model faces. The existing GPUI image bridge,
CPU display metadata and document-wide picking index remain; this does not claim
zero-copy UI composition, display LOD or a complete scene-delta protocol.

Regression coverage includes effective variant separation, shared payloads with
different bundle IDs, affine/reflection packing, visibility/wireframe policy,
large index-chunk winding/material preservation, real GPU buffer identity across
navigation/selection/moves, variant replacement and resource retirement, mirrored
front tint, per-instance edit isolation, perspective/orthographic line width,
black/material preference, partial-edge highlighting and near-plane clipping.
The existing real GPU shadow, AA and insertion-preview checks are retained.

  **723 passed** (302 core, 374 desktop library, five CLI, 42 IO); ten opt-in

- `cargo clippy -p meshcraft-core -p meshcraft-io -p meshcraft-desktop --all-targets --locked --offline -- -D warnings`: passed.

## 0.33.9 — Wall and mesh insertion latency

[Insertion profiling and the deferred-maintenance decision](insertion-performance.md)
record the user's large-drawing reproduction, affected-wall regeneration and
transaction-local mesh lookups. Wall/sweep commits fall from 20.9/25.0 seconds
to 0.54/0.77 seconds on the frozen fixture. Native frame capture still includes
whole-scene CPU refresh work; this patch does not implement an incremental
spatial overlay or idle compaction.
