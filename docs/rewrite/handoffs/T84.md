# T84 — Materials panel previews and material library

Status: **Complete**, 0.60.0 · C57.

## Request

The owner supplied a mockup of the Materials panel (`MaterialListItem` tiles: a
shaded sphere above the material name, three per row) and asked for:

1. Material items with a preview.
2. Two tabs: the materials in the model, and the material library that ships with
   the app.
3. Library sections: plain colors (red, orange, yellow, green, cyan, blue, magenta
   and fuchsia at 100% saturation and 25/50/75% lightness, plus greys every 10%),
   vegetation (foliage and grass, each normal, thick, tall, thick and tall) and
   construction (bluish and greenish glass; red, yellow and white brick; tiling of
   ½, 1, "1 and 1.2" and 2 units; fine and rough stone; 1-unit tiling with fine or
   rough stone; zinc and chrome).

The message ended after the metals; nothing past that point was implemented.

## Behaviour

| Point | Decision | Reason |
| --- | --- | --- |
| Previews | A unit sphere (72 segments, no edge lines) wearing the material, rendered off screen with the viewport's shaders on a background matching the tile | Shader materials must show their real look: brick, grain, reflections, blades |
| Where they render | The graphics owner, between viewport frames, with a second `lighting::Renderer` and a 176 px target; at most 40 ms per slice | The main renderer's prepared scene is keyed to its document; a second one never disturbs it, and the viewport keeps its frame rate |
| Cache | By a hash of the material without ID and name, its custom program and base material, and the texture folder if textured; least recently shown released past 240 | Edits re-render; renames and identical looks do not; textures wait for their asynchronous load |
| Requests | Only tiles on the visible tab | Nothing is rendered while the panel is closed or a tab is hidden |
| Still pictures | `RenderScene.backdrop`: background colour, no ground plane, no camera-target marker | The viewport always drew both |
| Tabs | Model (click makes current, double-click edits, existing buttons) and Library (sections, Add to Model, Apply to Selection) | Matches the mockup |
| Library IDs | Stable `library.…` IDs | Adding twice keeps the user's edited copy and only makes it current |
| Apply from library | Adds when missing and paints the selection as one Undo step | Same transaction as Paint's new-colour path |
| Menu use with nothing chosen | Opens the Library tab and fails with a reason | The menu has no tile to act on |
| Fuchsia | Hue 330°, magenta 300° | Both names usually mean #ff00ff; the owner listed them separately |
| "1 and 1.2 unit" tiles | 1½ units | Read as "1 and 1/2" between 1 and 2 |
| Thick / tall | Grass: density 75 and width 0.08 / height 1.6. Foliage: density 45 / leaves 0.8 long, 0.4 above the surface | "Thick" as denser, "tall" as longer |
| Zinc / chrome | Metal shader at reflectivity 0.6, polish 0.15 / 0.97, 0.98 | Matte grey versus mirror |

## Validation

`python3 scripts/verify_materials_panel.py` passed **all 10 checks** in a private
1280×900 software-GL desktop, writing screenshots and `observations.json` to
[references/materials-panel](../references/materials-panel/):

- Materials › Library lists Add and Apply Library Material;
- the Model tab shows rendered spheres (pixel variance, not a flat swatch), and
  saving `ansi-red` as blue renders its tile again in blue;
- the Library tab opens on plain colors with rendered spheres;
- double-clicking Red 50% adds `library.color.red-50` and marks it ✓;
- selecting Red 75% and pressing Apply to Selection adds it and paints a box (the
  material then refuses Delete Unused), and one Undo removes both;
- the viewport still delivers frames with no diagnostics after the library renders;
- `material.add_from_library` with no ID opens the Library tab with a reason;
- the application is still running.

`python3 scripts/verify_shader_library.py` still passes all checks.

Unit tests: library sections, counts, unique IDs, HSL samples and validity of every
library material in a document (`material_library.rs`); a sphere preview document
and a distinct picture key for every library material, and keys that follow the
look but not the name (`gpui_material_thumbnails.rs`); add, re-add keeping edits,
apply with one Undo, unknown IDs and the menu fallback (`materials_workflow.rs`).

Release gate: `cargo fmt --all --check`; `cargo test --workspace --locked`
(**852 passed, 25 ignored**, no failures); `cargo clippy --workspace --all-targets
--locked -- -D warnings` clean.

Python: stress, release (3 skipped), tool inventory and tool icon suites passed;
`export_tool_inventory.py --check` and `design_tool_icons.py --check` report no
drift (298 commands); `verify_plan.py` is valid.

`python3 scripts/stress/run.py --tiers small --samples 1 --only` over
`material.add_from_library`, `material.apply_from_library`, `material.apply`,
`material.delete`, `material.save` and `view.panel.materials.toggle` passed.
`material.edit` fails with "viewport rendering is pending" while the editor preview
holds the graphics owner. The released 0.58.0 binary, run with the 0.58.0 harness,
fails it the same way, so this predates T84 (as `material.new` did in T83); it is
recorded here, not fixed.

## Not verified

Hardware GL drivers were not tested; only Mesa software GL. The picture of a
textured material is checked only by its cache key, not rendered in the script.
