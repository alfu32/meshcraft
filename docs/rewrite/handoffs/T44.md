# T44 handoff

Status: **In progress**. Manual release tooling is implemented through **0.40.7**; full desktop feature/performance, installed-platform GUI and cross-platform release qualification remain open.

## Confined desktop startup — 0.40.9

The first 0.40.8 Snap launch exposed two Snap-specific details. snapd sets
`XDG_RUNTIME_DIR` to an app-private directory but leaves the connected Wayland
socket in its parent runtime directory. The preflight now checks that parent
only inside a Snap and restarts with the socket's absolute path, which Wayland
clients accept. If the socket is genuinely inaccessible, X11 remains the
fallback. The Snap's generated entrypoint also bypassed the Linux payload's
launcher, skipping its matched XKB library-pair environment; it now delegates
through that launcher and the GPU provider wrapper. Since the core24 base lacks
`/usr/share/X11/xkb`, the old-glibc payload now bundles the `xkb-data` tree and
points `XKB_CONFIG_ROOT` to it. Validation: formatting, Python syntax and locked
desktop `cargo check` pass. Full tagged-release and installed-Snap checks are
pending.

## Snap Wayland startup — 0.40.8

The strict Snap previously requested `x11` but not `wayland`, while GPUI selects
Wayland whenever `WAYLAND_DISPLAY` is set. An inaccessible socket therefore
reached GPUI's `NoCompositor` unwrap before graphics recovery. The Snap now
requests both display plugs. Before GPUI initialization, Linux startup probes the
advertised Wayland Unix socket and re-execs without Wayland variables when that
socket is unavailable and X11 is present. `cargo check --package
meshcraft-desktop --bin meshcraft --locked` and `cargo fmt --check` pass. Snap
Store installation and live compositor behavior still require release validation.

## Matched keyboard runtime — 0.40.7

The [native diagnosis run](https://github.com/alfu32/meshcraft/actions/runs/40235928668)
identified the same failure on both architectures: SIGSEGV in bundled
`libxkbcommon-x11.so.0`, through `xkb_x11_keymap_new_from_device`, during
`gpui::platform::linux::x11::client::X11Client::new`. GDB's loaded-library table
showed the Ubuntu 18.04 bridge beside the host core (Ubuntu 24.04 libxkbcommon 1.6),
while the host lacked its own X11 bridge. The bridge and core share private
structures, so resolving them independently across versions is unsafe.

The actual 0.40.4 CI x86_64 AppImage was reproduced in a network-isolated Ubuntu
24.04 container with the host X11 bridge deliberately removed: the mixed runtime
segfaulted (exit -11), and the same executable opened after selecting the matched
bundled pair. A second test using the actual new launcher, private library layout
and bundled Ubuntu 18.04 locale data also opened successfully without LD_PRELOAD.

Native packaging now places both fallback XKB libraries in `lib/xkb`, including
their audited licenses and unchanged glibc ceiling. The POSIX launcher preserves
coherent host/driver-provider library selection; missing or split XKB runtimes
prepend only the private pair. Bundled fallback locale data is selected with
XLOCALEDIR, preserving explicit XCOMPOSEFILE, per-user Compose files and explicit
XLOCALEDIR. All copied locale files retain the libx11-data copyright notice.
Four launcher regression tests cover missing, coherent and order-dependent split
pairs; all 13 release helper checks pass. The diagnostic workflow can apply the
checked-out launcher to old saved ELFs before a full release build, with its
test-only host-locale choice explicitly recorded. Complete native packages still
require the two offline release smokes on each Linux architecture.

## Native startup diagnosis — 0.40.6

The actual checksum-verified x86_64 0.40.4 CI AppImage passed the fixed offline
smoke locally (painted GUI and missing-driver message) and opened in a network-
isolated Ubuntu 24.04 container. Both 0.40.5 Linux CI checks nevertheless still
exited before displaying a GUI; the failed release was not published. Thus the
display race is real but does not explain the remaining CI-specific crash.

`appimage-diagnose.yaml` downloads the saved packages from a failed Release run,
checks their AppImage checksums, and captures direct and Firejail startup plus
native GDB traces on both Linux runner architectures. It rebuilds no application
and publishes only clearly marked diagnostic workflow artifacts. This avoids
guessing the cause from exit 139 or repeatedly rebuilding all release targets.

## AppImage offline startup — 0.40.3

[AppImage Hub PR 10772](https://github.com/AppImage/appimage.github.io/pull/10772)
rejected 0.40.1 after an early exit. The [Hub log](https://github.com/AppImage/appimage.github.io/actions/runs/40228506041)

both with and without network access: `No DRI3 support detected` and
`Failed to create surface: PlatformNotSupported`. Selecting Mesa Lavapipe allowed
the same AppImage to open offline. The Hub's exact low-level failure remains
unlogged, so this is reproduction of its conditions, not a claimed Hub retest.

The startup fix returns graphics initialization errors, catches only GPUI's
backend-constructor unwrap, and retries once in a fresh process with an installed
native-architecture Lavapipe manifest. Explicit driver choices remain intact.
Normal runtime/editor panics still propagate. Backend absence shows a driver-
independent X11 error window and exits 1 after acknowledgement.

Local native 0.40.3 tests under Firejail `--net=none` and private Xvfb verified a
painted full application window after automatic retry, plus the forced missing-
driver window and exit status 1. The release workflow now gates publication on
the same two actual-AppImage cases for both Linux architectures, with diagnostic
artifacts. Local native validation is not yet a published-AppImage Hub retest.

## Manual distribution pipeline — 2026-10-20

The [Release workflow](../../../.github/workflows/distribution.yaml) follows the Rust Kode six-target matrix and installer set, excluding Java/JDBC. Its reference is `alfu32/kodecraft` at `f3f915c5a9c14f445a3f4e83e520ce2970831636`; the requested sibling `../kode-rs` was absent, so the source was read from that repository.

- Runs only on manual dispatch at an existing tag. There is no tag/source input, tag-push trigger, automatic version edit or tag mutation. The tag must equal the hardcoded desktop app version and resolve to the checked-out commit.
- Uses the pinned Rust toolchain, locked Cargo dependencies and immutable source SHA across validation, all six builds and publication. Only publication has repository write permission.
- Builds Linux x86_64/aarch64, Windows x64/ARM64, and macOS Intel/Apple Silicon. Produces ZIP/tar.gz for all six, AppImage/Snap for Linux, MSI/MSIX for Windows and DMG for macOS: **22 primary artifacts**, each with a SHA-256 sidecar plus a combined checksum file.
- Native Linux compilation/dependency collection happens in a digest-pinned Ubuntu 18.04 container with a **glibc 2.27 ceiling**, not the supported hosted runner. `readelf` audits the CPU and actual maximum glibc symbol version of every bundled ELF. glibc/loader, compiler runtimes and graphics drivers stay external; non-driver libraries, a small DejaVu font set and notices are packaged with relative RPATHs.
- Portable archives carry per-file hashes and source/version/target metadata. Final publication requires every target/format, correct digests, matching metadata and actual executable format/CPU. Unit fixtures are explicitly synthetic and never published.
- Windows packages use WiX 5.0.2 and MakeAppx, with GPUI FXC shader compilation and static CRT. MSIX signing is intentionally deferred, without any secret references. macOS creates an app bundle and an ad-hoc signature; Developer ID/notarization is separate.
- Snap uses the reference's isolated `core24` runtime plus the `mesa-2404` graphics provider for OpenGL/Vulkan; this runtime is independent of the host-glibc portable/AppImage baseline.

[Packaging instructions](../../../packaging/README.md) explain tag dispatch, tool versions, library boundaries, signing and runtime constraints. Source icons/shaders stay embedded; packaging copies only explicit binaries/docs/notices/example inputs, not user scenes or configuration. Root license texts reflect the existing workspace `MIT OR Apache-2.0` declaration.

## First native CI run and fixes — 0.5.2

Inspected the [0.5.1 release run](https://github.com/alfu32/meshcraft/actions/runs/39414511730) with `gh run view` and downloaded each failed job log using `gh api repos/alfu32/meshcraft/actions/jobs/<id>/logs`.

- Both Linux targets compiled optimized binaries, passed native glibc/architecture audits and assembled portable archives. Both then failed in `appimage.py` creating `target/installer-tools`: Docker had created host `target` as root. The fix pre-creates writable mounts/output directories and runs **both** validation and release containers as the runner UID/GID, with a dedicated Cargo home that does not expose host rustup proxies. No old-glibc requirement is relaxed.
- Both Windows targets compiled Rust/C but failed at the final link with raylib `__imp_fmaxf`, `__imp_fopen` and other C runtime imports. Rust requested static CRT while CMake's runtime target property still selected dynamic CRT. `packaging/windows/static-crt.cmake` selects `MultiThreaded` (with the Debug variant) and disables GLFW's DLL runtime, matching Rust `+crt-static`.
- Both macOS jobs eventually succeeded, including portable archives and DMGs. Intel took approximately 27 minutes; Apple Silicon approximately 12 minutes. Installed GUI behavior remains untested.
- Validation alone took **32 minutes** (23m12s tests + 7m26s Clippy, plus setup) and blocked all native builds. Build jobs now depend only on preparation; publication still requires successful validation and the full native matrix. Validation uses an unoptimized, no-debug-info development profile; release optimization is unchanged. Compile concurrency increases from two to four. Immutable-pinned cache restore/save actions retain Cargo inputs and compiled outputs by native configuration/lockfile, including partial builds before installer failures. GitHub cache ref isolation means retries benefit directly; different version tags still need a cold build without a compatible default-branch seed.

Local checks for this fix: eight release contract tests, actionlint, plan/link validation and diff checks pass. A Windows-target CMake/clang-cl configure probe generates `-MT`, with no `-MD`, using the actual toolchain file. The corrected container ownership and inner Cargo configuration are checked separately before dispatching the next tagged run.

## Native dependency reduction and second Windows failure — 0.5.3

The [0.5.2 run](https://github.com/alfu32/meshcraft/actions/runs/39422621294) passed validation, both Linux installer jobs and both macOS jobs. Windows ARM64 got past the CRT errors and exposed a duplicate `ShowCursor` symbol: raylib defines that C function, and the unused winit backend imports Win32's function under the same name. Source inspection finds the Win32 call in `winit` and no corresponding GPUI call.

The main desktop is already GPUI/raylib. Eframe is now a **wasm-only** dependency; shared session, viewport and headless UI tests depend directly on the same locked egui version. Browser-only constructors, storage adapter and the eframe `App` implementation are gated accordingly. This removes native eframe, egui-winit, winit, egui-wgpu and wgpu 30 from the desktop graph, addressing the observed symbol collision and unnecessary cold compilation. No linker duplicate-symbol suppression or edits to Cargo's registry sources are used. GPUI/raylib rendering and the model/tools stay in place.

Executed locally: `cargo test --workspace --locked --offline` (495 passed, two ignored); `cargo clippy --workspace --all-targets --locked --offline -- -D warnings`; `cargo build -p meshcraft-desktop --locked --offline`; and `cargo check -p meshcraft-desktop --target wasm32-unknown-unknown --locked`. The browser check passes with existing target-specific warnings. Downloaded the actual 0.5.2 Linux x86_64 CI artifact, verified every primary artifact checksum and both portable manifests, confirmed glibc 2.27 metadata, and executed the AppImage with `APPIMAGE_EXTRACT_AND_RUN=1 --version` successfully. The native 0.5.3 GPUI/raylib application also opened the dynamic-object example on isolated Xvfb using software Vulkan/OpenGL and separate XDG settings; the [capture](../references/release/native-without-eframe.png) shows the full interface, shaded geometry and hotspots with the offscreen context kept hidden. This is a UI smoke check, not a performance measurement. The next tagged matrix must verify the new Windows graph and installer stages.
