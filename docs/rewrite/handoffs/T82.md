# T82 — Shader objects from scratch

Status: **Complete**, 0.58.0 · C55.

## Request

The owner asked why there was no generic shader editor for defining shader objects
from the ground up, why New Shader Object always started from a prototype, and
whether there were hidden layers. There were: New Shader Object was the procedural
tree command under a new label, always seeded with the built-in branching preset,
and the author's GLSL was spliced into a host template, a tree engine and, for
branching, a transform-feedback state pass, none of which the editor showed. The
owner approved a blank object kind, a read-only Full Source tab, New Shader Object
opening the editor on a blank template with a choice of start, and renaming Bake to
Shader to Bake to GPU Mesh.

## Behaviour

| Point | Decision | Reason |
| --- | --- | --- |
| Blank object | `generation: "custom"`: `customVertex(vertexId, instanceId, …)` writes every vertex | Geometry from the ground up; GL 3.3 has no other stage that creates vertices |
| Counts | `vertexCount` (multiple of 3, ≤ 65,536) per instance; `instances` fixed or an integer parameter | Mirrors instanced drawing, so parametric objects need no CPU work |
| Limits | Candidate budget and 6,000,000 vertices; zero instances draw nothing and refuse to bake | Same safety limit as GPU bake capture |
| Bounds | Required `objectBounds`; each coordinate a number or expression over parameters | Culling, picking and Fit Model run on the CPU without the shader; first run showed fixed bounds framing one box of a five-box stack |
| Template | No tree engine or tree outputs in custom programs; omitted `proceduralVertex`/`proceduralColor` get pass-through defaults | A blank object contains only what the author writes plus the host template |
| Full Source | Read-only tab with the exact viewport vertex and fragment shaders, copyable; branching adds a note on its state pass | Nothing hidden |
| New Shader Object | Opens the editor on the blank object; Start from lists a blank surface and every built-in | Blank by default, as asked; trees remain one choice away |
| Built-ins | Unchanged built-in objects use the built-in program; edited ones are saved as `custom.<kind>.<n>` | Creating a tree doesn't copy the branching program each time; built-ins stay read-only |
| Create Object | Program (when new) and prototype in one Undo step, then placement | One action, one undo |
| Materials › New Shader | Same editor from a blank surface; saving an unchanged built-in stores a copy | Consistent with the old Edit Program behaviour |
| Rename | Bake to GPU Mesh, New Shader Object, Shader Object Settings; IDs `object.bake_to_shader`, `object.new_tree`, `object.edit_tree` unchanged | MCP clients, stress suite and saved scripts keep working |
| Baked objects | Unaffected: they store triangles, not programs | Answered before implementation |

## Validation

`python3 scripts/verify_shader_objects.py` passed **all 23 checks** in a private
1280×900 software-GL desktop, writing screenshots and `observations.json` to
[references/shader-objects](../references/shader-objects/). It covers the renamed
catalog labels; the blank preview (1 instance, no diagnostics); Full Source copied
through the X clipboard (10,188 characters, both shaders, the author's
`customVertex`, no tree engine, typed text ignored); switching to the built-in Tree
and back; Create Object as one Undo step followed by placement; Bake to Mesh (12
triangles), Undo and Bake to GPU Mesh (12 triangles); a parameter-counted stack
(5 instances plus the box) whose expression bounds reach y = 5; Materials › New
Shader; and a tree created from the unchanged built-in with no program copy.

GPU tests under `LIBGL_ALWAYS_SOFTWARE=1 xvfb-run -a`, `--ignored --test-threads=1`:
`gpu_bake_custom_object_geometry_counts_and_bounds` (3 stacked boxes, 36 triangles,
outward winding, bounds 0–3, zero count rejected), run with every other
procedural, branching, preview and bake GPU test: **11 passed**.

`python3 scripts/stress/run.py --tiers small --samples 1 --only` the seven affected
commands passed (partial coverage by design; full coverage is the release
workflow's job).

Release gate passed: `cargo fmt --all --check`;
`cargo test --workspace --locked` (**843 passed, 24 ignored**, no failures);
`cargo clippy --workspace --all-targets --locked -- -D warnings` (two findings in
the new validation code and one in a new test were fixed, not suppressed; tests
were rerun afterwards with the same result).

Python: stress (17), release (19, 3 skipped), tool inventory (4) and tool icon (3)
suites passed; `export_tool_inventory.py --check` reports no drift;
`verify_plan.py` is valid.

## Not verified

The shader editor's code panes were driven by clicks and the clipboard, not by
typing a new program through the UI; programs with other shapes were exercised
through MCP and unit tests. Hardware GL drivers were not tested; only Mesa
software GL.
